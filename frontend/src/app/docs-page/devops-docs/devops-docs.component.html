Fundamentación Filosófica y Metodológica: DevOps vs. CI/CD

Para garantizar la estabilidad dimensional, la integridad algorítmica y la velocidad de entrega del proyecto, se adoptó un enfoque basado en la cultura DevOps. Con el fin de evitar ambigüedades operativas, la arquitectura del sistema establece una relación de inclusión estricta entre ambos conceptos:

DevOps (El Marco Metodológico)

Una filosofía cultural y operativa que unifica el desarrollo de software (Dev) con las operaciones de sistemas (Ops). Su objetivo es automatizar y optimizar todo el ciclo de vida para entregar incrementos de software de alta calidad de forma continua, segura y predecible.

CI/CD (El Motor Técnico)

La implementación táctica y tecnológica que hace viable la cultura DevOps. Se compone de tuberías lógicas (pipelines) automatizadas que se ejecutan de extremo a extremo sin necesidad de intervención humana.

Arquitectura del Pipeline de Automatización

El ciclo de vida del código fuente está regido por un flujo automatizado que reacciona instantáneamente a cada actualización en el repositorio. Este proceso mitiga el riesgo del "síndrome de la máquina del desarrollador" (código que funciona localmente pero falla en producción) dividiéndose en dos grandes macro-fases secuenciales:

CI

A. Integración Continua (Continuous Integration)

Cada evento de actualización (git push) dirigido a la rama principal main desencadena esta fase de forma mandatoria y restrictiva:

  • Instanciación y Checkout: El servidor en la nube (Runner) inicializa un contenedor virtual limpio y efímero basado en Ubuntu Linux y clona el código fuente.
  • Configuración del Entorno: Se aprovisiona el contenedor inyectando el intérprete de Python en su versión exacta y se descargan las dependencias.
  • Ejecución de Pruebas Unitarias: Se invoca de forma automatizada la suite de aseguramiento de la calidad mediante el motor Pytest.
Efecto Circuit Breaker: Si una sola prueba falla, el pipeline se interrumpe inmediatamente (exit code != 0), notificando el error y protegiendo la rama de producción contra código corrupto.
CD

B. Despliegue Continuo (Continuous Deployment)

Si, y solo si, la suite de pruebas devuelve un estado de éxito rotundo (SUCCESS), la tubería avanza de forma síncrona a la fase de distribución automatizada:

  • Construcción de Artefactos: Se procesan y empaquetan los recursos listos para producción (vistas HTML, estilos distribuidos, lógica interactiva en JS y las dependencias dinámicas del Dashboard).
  • Publicación Automatizada: El motor realiza el despliegue de los artefactos en los servidores de infraestructura perimetral de GitHub Pages.
Cero Despliegues Manuales: La última versión estable del software queda expuesta al cliente de manera inmediata y transparente, erradicando los despliegues tradicionales por FTP o SSH.

Historial de Ramas del Proyecto

El repositorio ha evolucionado a través de distintas ramas que reflejan las etapas del proyecto. A continuación se detalla el propósito y la cronología de cada una:

main Rama Original

Rama principal inicial del proyecto. Albergaba el sitio web original de GitHub Pages con un index.html estático, CSS y JS planos. Fue el punto de partida antes de cualquier migración o automatización.

angular-migration Migración

Rama dedicada a la migración de la aplicación desde HTML estático hacia Angular. Aquí se reescribió toda la interfaz como una SPA moderna con componentes, enrutamiento y las herramientas del ecosistema Angular.

TestAuto CI/CD + Testing

Rama de desarrollo y mejora del pipeline de CI/CD. Aquí se implementaron los test automatizados con Pytest, la configuración de GitHub Actions para integración continua, y la validación automática de calidad de código antes del despliegue.

gh-pages Deploy

Rama de despliegue automatizado. Contiene el build compilado de la aplicación Angular listo para ser servido por GitHub Pages. Es actualizada automáticamente por el pipeline de CD cada vez que se valida exitosamente la integración continua. Es la única rama que ve el usuario final.

Flujo Evolutivo: main (sitio estático) → angular-migration (SPA Angular) → TestAuto (CI/CD + Tests) → gh-pages (deploy automático)

Telemetría del Pipeline: Monitoreo Asíncrono de Doble Nivel

En concordancia con el pilar de Monitoreo Continuo de la cultura DevOps, la aplicación implementa un motor de telemetría embebido directamente en la terminal interactiva del cliente (js/app.js). Este componente elimina la necesidad de consultar paneles externos, consumiendo de forma asíncrona la API REST de GitHub v3 mediante un patrón de consulta encadenada de doble nivel:

1. Nivel Superior (Workflow Runs API)

El script intercepta dinámicamente las propiedades window.location.hostname y window.location.pathname para deducir de forma autónoma el propietario y el repositorio actual. Con esta información, consulta el endpoint /actions/runs?per_page=1 para extraer los metadatos globales de la ejecución:

  • Número de ejecución y autor del push.
  • Mensaje del commit y hash abreviado (head_sha).
  • Estado del contenedor (queued, in_progress, completed) y conclusión final (success, failure), mutando el color del Badge de Estado Superior en tiempo real.

2. Nivel Interno (Jobs & Steps API)

Utilizando la URL dinámica inyectada en el payload anterior (run.jobs_url), el script realiza una segunda petición asíncrona para inspeccionar el contenedor por dentro. El algoritmo implementa un ciclo iterativo (forEach) que mapea en vivo el arreglo de tareas individuales (steps) configuradas en el archivo YAML.

Cálculo Dinámico de Compilación: Extrae las marcas de tiempo ISO de alta precisión (started_at y completed_at). Mediante diferencias de milisegundos, el script calcula e imprime en la consola del Dashboard la duración exacta en segundos de cada fase operativa, mutando los estilos CSS de la terminal (Verde para éxito, Azul para procesos activos, y Rojo para fallas).

Mecanismo de Tolerancia a Fallos (Circuit Breaker Estético):
Conscientes de las restricciones de red, firewalls o el uso de VPNs institucionales durante las fases de evaluación y sustentación, la consola cuenta con un bloque robusto de manejo de excepciones (try/catch). Si la conexión asíncrona con el servidor de GitHub se bloquea o sufre de alta latencia, el sistema intercepta el error inmediatamente y conmuta a un estado de Caché Local de Contingencia, pintando una simulación fluida y estable para proteger la continuidad de la presentación sin congelar la interfaz web.

Ventajas de la Arquitectura Implementada

La adopción estratégica de esta infraestructura e integración DevOps se traduce en beneficios cuantitativos y cualitativos inmediatos para el proyecto:

  • Mitigación Completa del Error Humano: El proceso de validación e inyección a producción está blindado en su totalidad por código explícito, impidiendo fallas catastróficas por descuidos de empaquetado o configuraciones de entornos locales.
  • Garantía Estricta de No Regresión: Al requerir que el paso por la suite de pruebas unitarias sea obligatorio para habilitar el despliegue, se asegura matemáticamente que las nuevas características añadidas al sistema no rompan algoritmos de diseño paramétrico, de simulación o flujos de interfaz que ya funcionaban con anterioridad.
  • Trazabilidad Absoluta y Auditoría: Cada ciclo DevOps reflejado en la consola interactiva está indexado unívocamente con el Hash del commit de Git. Esto permite un control transparente y una auditoría directa para determinar qué cambio exacto provocó el estado actual de la plataforma de producción.
